## 1.1 · CARTO — the Light basemap is watermarked in production right now

**This is the single most visible thing wrong with the product today, and it is new since the
last session.**

**Where:** `src/app/parcels/map/page.tsx:167-181`, `STYLES.light`, three subdomains
`a|b|c.basemaps.cartocdn.com/light_all/{z}/{x}/{y}.png`.
**Who sees it:** everyone. `page.tsx:2107-2108` sets the default basemap to `light`
(`useRef<BaseMap>("light")` / `useState<BaseMap>("light")`).

**Verified three ways:**

1. Direct `GET https://a.basemaps.cartocdn.com/light_all/12/2405/1596.png` → HTTP 200,
   `image/png`, 14,122 bytes. I opened the image: it carries a large diagonal
   **`API KEY REQUIRED` / `carto.com/basemaps/apikey`** watermark across the tile.
2. The same request carrying `Referer: https://www.zaahi.io/parcels/map`, an `Origin`
   header and a real Chrome UA returns a **byte-identical** file
   (both `md5 67346c4262b3edf39cd05be8bf4b03a4`). So this is **not** referrer-scoped and
   **not** a quota that a real browser escapes.
3. Headless Chromium against `https://www.zaahi.io/` issued **42** `light_all` tile
   requests, all HTTP 200 — i.e. production is actively pulling watermarked tiles.

`dark_all` is watermarked too (checked, same watermark) — but Dark no longer uses CARTO,
so that no longer matters.

**Two methods disagree — reporting both, as instructed.** Commit `73c0751`
(2026-08-28) carries this in its own source comment:

> *"It could not be reproduced from here — direct fetches, fetches carrying a zaahi.io
> Referer, and a real Chromium switching to Dark all returned clean 200s (24 tiles, 0
> failures) — which points at a CARTO free-tier quota that trips under sustained real-user
> load from one referrer."*

That reading was reasonable on 28 Aug and is **wrong today**. The reconciliation: CARTO
began requiring an API key for raster basemaps and watermarking anonymous tiles in **late
August 2026** — the rollout was mid-flight on the 28th and is complete now. The same change
hit Grafana's Geomap panel, Home Assistant and openHAB in the same window.

**Terms of the free tier (current):** a key is free, issued instantly at
`carto.com/basemaps/apikey`, **does not require a CARTO account**, and carries a fair-use
limit of **5 million tile requests / month**. Above that, commercial licensing.
CARTO has also signalled it may stop updating the raster basemaps entirely and that the key
requirement is coming to the vector basemaps next.

**Attribution:** `© CARTO © OpenStreetMap contributors` is present and correct in the style.

**Options, cheapest first:** request the free key and append it; or move Light to Esri's
**Light Gray Canvas**, symmetric with what `73c0751` already did for Dark, so the map has one
provider instead of two; or self-host. The second removes the dependency class rather than
renewing it — but see 1.2 before treating Esri as a safe harbour.

**Also:** `src/lib/basemaps.ts` still hard-codes CARTO for *both* dark and light. Nothing in
`src/` imports it (`BASEMAPS` / `BASEMAP_ORDER` have zero consumers). It is dead code — and
it is the file a reader would naturally "fix" first, to no effect.

**Where:** `page.tsx:150-220`. Four endpoints, all on `server.arcgisonline.com`:

**Terms — the part that matters:** Esri's developer documentation puts the
`services.arcgisonline.com` / `server.arcgisonline.com` legacy tile services in **"mature
status"**: no longer updated, and applications were told to migrate to the authenticated
ArcGIS basemap services (API key / ArcGIS Location Platform account) **by 2022-04-30**.

basemap and data attribution**.

**So:** on 28 Aug we moved Dark off a provider that had just started requiring a key, onto a
provider that has required one since 2022 and simply hasn't enforced it on the legacy
endpoint. That is the same failure mode, one step later. No shutdown date is announced —
**UNVERIFIED whether Esri intends one.**

**Attribution gap (new finding):** the `esriDarkLabels` source has **no `attribution` field
at all**, and Satellite credits only `© Esri World Imagery` where World_Imagery's own credit
line is `Esri, Maxar, Earthstar Geographics`. Ironically the dead `src/lib/basemaps.ts` has
the fuller string. Low severity, but it is a stated licence condition.

## Data integrity — issue #21, the 215-row vault

**I cannot quantify this from here, and I will not guess.** The vault lives only in Supabase.
There is no snapshot in `data/`, none in git, and every API that serves it returns 401 without
a session. Reading it means `DATABASE_URL` — a production credential, out of scope for this pass.

**What is on record** (triage of task `20260828-033112-e6366e`, 2026-08-28), quoting the
founder report verbatim:

> *"The 215-listing vault has bad records: placeholder plot IDs 000000, 000001, 000002,
> 300001, 12111, 12121, several 0 AED prices, duplicated Dubai Islands entries and
> district/project name mismatches."*

So: **215 rows total**, **6 named placeholder IDs**, **"several"** zero prices (never counted),
**duplicate Dubai Islands rows** (never counted), district/project mismatches (never counted).

**What I verified in source — why they got in:**

- `src/app/api/me/vault/entries/route.ts:73` validates `plotNumber` with `^\d{5,10}$`. That
  accepts `000000`, `000001`, `000002`, `300001` — and `12111`/`12121` are legal 5-digit
  numbers, so no regex will ever exclude them; they need a domain check.
- `askingPriceFils` is validated with `^\d{1,16}$`, which **accepts `0`**.
- The uniqueness key is `(ownerId, emirate, district, plotNumber)` — so the *same* plot filed
  under a *different* district label is not a duplicate by construction. That is exactly the
  "duplicated Dubai Islands entries + district mismatch" pattern the founder saw.

**Exact query to quantify it** (read-only, run it yourself against a read replica or with a
read-only role):

```sql
SELECT
  count(*)                                             AS total,
  count(*) FILTER (WHERE "askingPriceFils" IS NULL
                      OR "askingPriceFils" = 0)        AS zero_or_null_price,
  count(*) FILTER (WHERE "plotNumber" ~ '^0+[0-9]*$')  AS leading_zero_placeholder,
  count(*) FILTER (WHERE "plotNumber" IN
        ('000000','000001','000002','300001','12111','12121')) AS named_placeholders
FROM "VaultEntry";

-- duplicates that the unique key misses (same plot, different district label)
SELECT "plotNumber", count(*) AS n,
       array_agg(DISTINCT "district") AS districts
FROM "VaultEntry"
GROUP BY "plotNumber"
HAVING count(*) > 1
ORDER BY n DESC;
```

triage plan already says so explicitly: *"do not delete or rewrite any row until the founder
