## How the session was mocked

`/parcels/map` is wrapped in `AuthGuard`, which redirects to `/` unless
`supabaseBrowser.auth.getSession()` returns a session with
`user_metadata.approved === true`. supabase-js reads that session from
`localStorage` under `sb-<projectRef>-auth-token`.

The harness (`tests/e2e/harness.ts`) patches `Storage.prototype.getItem` in a
`page.addInitScript`, so **any** key matching `/^sb-.+-auth-token$/` returns a
synthetic approved session; `setItem` ignores writes to those keys so the app
cannot clobber it. Consequences that matter:

- **No project ref is hard-coded**, so nothing about the real Supabase project
  lands in the repo and the harness survives a project change.
- **Nothing is written to real storage** and **no request ever reaches Supabase
  auth** — the stub is read-side only, inside one browser context.
- The synthetic JWT is a structurally valid *unsigned* token with an obviously
  fake payload (`e2e@harness.invalid`). It is never presented to real auth,
  because every `/api` call is intercepted before it leaves the browser.

## Why no production data was touched

Stronger than the read-only constraint required: **the production database was
contacted zero times.**

Every `/api/**` request is fulfilled from fixtures *inside the browser*, so the
Next route handlers never execute and Prisma is never constructed. Specifically:

- Non-GET requests are aborted and recorded as failures — a mutating call
  cannot pass silently.
- Any endpoint without a fixture is aborted and recorded, so a forgotten route
  fails the run rather than escaping to production. Check (d) asserts that list
  is empty, which is what caught `/api/vault/shared-with-me` and
  `/api/archie/reverse-district` during harness development.
- `/tiles/**` and `/glb/**` are short-circuited.

No account was created, no sign-up performed, and no `/api/notify-admin` call
was made. The harness seeds and cleans up nothing, because it has nowhere to
seed to.

Fixtures (`tests/e2e/fixtures.ts`) are five parcels chosen to exercise the exact
branches under test: four distinct statuses **including `VAULT_PRIVATE`**, one
parcel with `geometry: null`, and one large polygon centred on a pinned camera
so a canvas-centre interaction is deterministic.

### (e) — what is and is not verified

**Verified at runtime:** the readout updates as the pointer moves, and DOM
mutation volume during sustained movement stays low.

**UNVERIFIED — reason:** "no full-page re-render" cannot be *proved* from
outside the app. React DevTools' commit profiler is not scriptable from
Playwright, and a re-render that produces identical output causes no DOM
mutation, so mutation counting is corroborating evidence, not proof. Proving it
directly would need a render counter compiled into `ParcelsMapPageInner`, i.e.
shipping test scaffolding in production code.

What stands instead is a **static guarantee**: the page-level `cursor` state and
its `map.on("mousemove", … setCursor)` feeder no longer exist (`grep` for
`setCursor` in `src/` returns nothing), so there is no code path by which a
pointer move can set state on the page component. The re-render cannot happen
because the mechanism was removed, not because it was measured as absent.

### (f) — one filtered line

`[Vercel Speed Insights] Failed to load script from
/_vercel/speed-insights/script.js` is filtered. It is emitted by the
`@vercel/speed-insights` vendor script and only fires **off** Vercel, where
that path does not exist; on the real deployment the script loads and the
message does not appear. Filtered as vendor/environment noise, not as an app
log. MapLibre/WebGL/SwiftShader chatter is filtered on the same basis.

## Forward-fixes the verification surfaced

All three are in `af90138`. **None of them was visible to static review** — this
is the argument for the harness existing at all.

### 1. `MapCoordsReadout` never subscribed to the map — the readout was dead

`src/app/parcels/map/MapCoordsReadout.tsx`

React flushes **child** effects before the **parent's**, and
`ParcelsMapPageInner` constructs the map inside its own effect. The extracted
readout therefore ran its effect while `mapRef.current` was still `null`, hit
the early return, and — with a stable `[mapRef]` dependency — never retried. The
component mounted and rendered its initial `25.20000, 55.27000`, so it looked
correct in a screenshot, but it never moved.

This shipped in `78e6612` (the perf-item-2 extraction) and would have reached
production as a **functional regression against the very readout the change was
meant to preserve**. The rAF loop — already running every frame — now performs
the attach on the first frame the map exists, which is the same read-`mapRef`-live
discipline `MapZoomReadout` uses and the reason that component never had the bug.

### 2. `attachOverlays` re-fetched every enabled overlay on a cold load

`src/app/parcels/map/page.tsx`

`attachOverlays` cleared `loadedLayersRef` unconditionally before reloading.
That is correct **after a basemap swap**, where MapLibre has wiped the source
registry — but wrong on the initial attach:

1. the `[layers]` effect runs on mount (`mapRef.current` is already set by then
   — the same effect-ordering that produced the `[baseMap]` duplicate) and
   loads the layer;
2. the map-init `load` handler then reaches `attachOverlays`, **deletes** that
   record, and fetches the same GeoJSON again.

`loadLayer`'s in-flight guard could not collapse them because the two are
sequential, not concurrent. Now gated behind an explicit `opts.reattach`, passed
only by the basemap-swap and WebGL-context-restore paths.

**Metro: 2 fetches → 1.** This is *pre-existing*, not introduced by the
integration — before the mount guard it was worse still. Check **(d3)** was added
specifically so that dropping the `reattach` flag can never silently make
overlays disappear on a theme change.

### 3. `SidePanel` close control had no accessible name

`src/app/parcels/map/SidePanel.tsx` — a bare `×` button. A screen reader
announces "multiplication sign" or skips it. Given `aria-label="Close parcel
panel"`, which also gave the harness a stable handle. One attribute; noted here
because it is a product change, however small, that you did not ask for.

### Harness-side issues (not product defects)

Recorded so the harness is not mistrusted later: the terms modal key stores the
literal `"true"` (not `"1"`); `getByText(/Vault Private/i)` matched both the
group heading and the card chip; `<aside>` counting had to become *on-screen*
counting because `SidePanel` is always mounted and merely parked off-canvas with
a `translate` — a raw node count is always ≥ 1 and would have made check (c)
meaningless.

## Repeatability

```
pnpm build && pnpm test:e2e
```

`playwright.config.ts` starts `next start -p 3100` itself and tears it down.
Deliberately a **production** build, because check (f) is specifically about the
production console — a dev server's React warnings and HMR chatter would make
that check vacuous. Single worker, no parallelism, because (d)/(d3) assert on
per-load request counts.

`@playwright/test` is pinned at `1.62.1` as a devDependency — the version whose
bundled chromium revision (1234) matches the browser already cached on this
machine, so no browser download is required. No other dependency changed.

**One operational note:** do not run `pnpm build` while a `next start` is
serving the same `.next` — the running server keeps a stale manifest and every
chunk 400s. CLAUDE.md warns about this for `pnpm dev`; it applies to
`next start` too. Build first, then start.
