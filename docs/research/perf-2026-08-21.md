## Causes, ranked

### CAUSE 1 · The map initialises twice on every load — `[baseMap]` effect calls `setStyle` during mount

**Severity: High · Confidence: Proven · Cost: load-time (doubles nearly all load work)**

Two effects in `ParcelsMapPageInner` collide on the first mount:

| Step | Proof |
|---|---|
| Effect **A** (`deps: []`) creates the map | `page.tsx:4340` (effect), `:4351` (`new maplibregl.Map`), `:4353` (`style: STYLES.light`) |
| …registers the load handler | `page.tsx:4435` `map.on("load", async () => {…})`, closing at `:4941` |
| …assigns the ref **synchronously in the effect body** | `page.tsx:4943` `mapRef.current = map;` |
| Effect **B** (`deps: [baseMap]`) is declared *later in the same component* | `page.tsx:5121`, deps at `:5159` |
| …so React runs it in the **same mount commit**, right after A. Its guard cannot fire | `page.tsx:5122-5123` `const map = mapRef.current; if (!map) return;` — already non-null |
| …and it calls `setStyle` unconditionally, with **no first-mount guard** | `page.tsx:5124` `map.setStyle(STYLES[baseMap]);` |
| …re-applying the **identical** style: initial `baseMap` state is `"light"` | `page.tsx:1885` `useState<BaseMap>("light")` vs `:4353` `style: STYLES.light` |

React flushes passive effects in hook-declaration order within a commit, and A is declared at
`:4340`, B at `:5121`. There is no path where B runs before A.

**MapLibre does not short-circuit the redundant `setStyle`.** From the installed
`maplibre-gl@5.22.0` bundle:

- `setStyle(e,i)` → `…diff && this.style && e ? this._diffStyle(e,i) : this._updateStyle(e,i)` — no
  style-equality check. `STYLES` are inline `StyleSpecification` objects (`page.tsx:83`), so
  `_diffStyle` goes straight to `_updateDiff`.
- `_updateDiff` → `this.style.setState(e,i)` → `_checkLoaded()` → `if(!this._loaded) throw new Error("Style is not done loading.")`
- caught → `warn("Unable to perform style diff: … Rebuilding the style from scratch.")` → **`this._updateStyle(e,i)`** — a full style teardown and rebuild.

That warning is precisely the one recorded in audit 1.7, and it is not incidental: it is the
receipt for a from-scratch style rebuild on first paint. It is also the mechanism behind
**audit 1.8** (blank canvas for 3–8 s with no loading indicator) — the canvas has nothing to paint
while the style it just built is thrown away and rebuilt.

**Consequence: the entire `map.once("styledata")` body (`:5125-5158`) runs *in addition to* the
entire `map.on("load")` body (`:4435-4941`).** Everything below is doubled per load:

| Doubled work | Call sites | Predicted count | Audit 5.6 observed (2026-08-18) |
|---|---|---|---|
| `loadZaahiPlots` → `apiFetch("/api/parcels/map")` at `:3177` | `:4574` (load) + `:5151` (styledata) | ×2, **+1** from `ParcelsNav.tsx:84` = **×3** | **×3** ✅ |
| 197 plot + 456 extrusion features rebuilt, incl. per-tier `scaleRingFromCentroid` trig | build loop from `:3195`; log at `:3439` | ×2 | ×2 (console) ✅ |
| GeoJSON re-uploaded to GPU via `setData` | `:3467` (plots), `:3546` (buildings) | ×2 | — |
| `attachOverlays` → **deliberately clears the loaded-set then re-fetches** every enabled layer | `:4568` + `:5147`; the clear is `:4259` `loadedLayersRef.current.delete(def.key)` | ×2 per enabled layer | `/api/layers/metro` **×2** ✅ |
| `loadVaultShared` → `apiFetch("/api/vault/shared-with-me/map")` at `:3754` | `:4580` + `:5154` | ×2 | **×2** ✅ |
| `ensureDistrictNamesLayer` → `apiFetch("/api/layers/communities")` at `:4278` | `:4266`, reached from both `attachOverlays` calls | ×1 **or ×2 — races** | — |
| `loadAmenityIcons` (idempotent per image, but the rebuild wipes them) | `:4567` + `:5146` | ×2 | — |
| `addLandTileSource` ×3 PMTiles sources | `:4664-4666` + `:5137-5139` | ×2 | — |

The `ensureDistrictNamesLayer` cache (`districtNameFeaturesRef`, checked at `:4276`) is a
check-then-fetch with an `await` in between, and the two `attachOverlays` calls run on independent
async chains — so both can observe `null` and both fetch. It is a race, not a guaranteed double.

**Proposed fix** (do not implement without founder sign-off on the basemap path):

Give effect B a first-run guard so it only reacts to *changes* in `baseMap`, not to mount:

```ts
const baseMapInitRef = useRef(true);
useEffect(() => {
  if (baseMapInitRef.current) { baseMapInitRef.current = false; return; }
  const map = mapRef.current;
  if (!map) return;
  map.setStyle(STYLES[baseMap]);
  map.once("styledata", async () => { /* unchanged */ });
}, [baseMap]);
```

This is a ~4-line change that removes one full style rebuild, one `/api/parcels/map` round trip,
one `/api/vault/shared-with-me/map` round trip, one re-fetch of every enabled `/api/layers/*`,
one 197-parcel/456-feature geometry build, and two GPU source uploads — per load.

> **Do not** reach for SWR/React Query here, which is what audit 5.6 proposes. A request cache would
> hide the duplicate *fetches* while leaving the duplicate style rebuild, the duplicate geometry
> build and the duplicate GPU upload fully in place. 5.6 and 1.7 are not two problems; they are one
> problem with two sets of symptoms, and it has one four-line fix.

The residual third `/api/parcels/map` (`ParcelsNav.tsx:81-88`) is a separate, deliberate choice —
`ParcelsPortalPanel.tsx:48-53` documents the same decision and gates its copy behind first-open.
`ParcelsNav` does not. Lifting both to a shared parent value is a follow-up, not part of this fix.

### CAUSE 2 · Every mouse move re-renders the entire ~6,300-line page component

**Severity: High · Confidence: Proven mechanism, unmeasured magnitude · Cost: continuous, during interaction**

This is the strongest candidate for the *stutter* specifically. CAUSE 1 is a load-time cost;
this one is paid continuously, at pointer frequency, for as long as the cursor is over the map.

| Fact | Proof |
|---|---|
| A raw global mousemove handler writes React state | `page.tsx:4387` `map.on("mousemove", (e) => setCursor({ lng: e.lngLat.lng, lat: e.lngLat.lat }));` |
| `cursor` is page-level state in `ParcelsMapPageInner` | `page.tsx:1903` `const [cursor, setCursor] = useState({ lng: 55.27, lat: 25.20 });` |
| A **fresh object literal** every event → `Object.is` never matches → React can never bail out | `page.tsx:4387` |
| The component is ~6,300 lines with 57 `useState`, 30 `useEffect`, 33 `useRef`, 7 `useMemo` | `page.tsx:1637` (`function ParcelsMapPageInner`) → `:7937` |
| Its **only** consumer is one coordinate readout | `page.tsx:5883` `{cursor.lat.toFixed(5)}, {cursor.lng.toFixed(5)} · z<MapZoomReadout …/>` |
| **Zero** `React.memo` under `src/app/parcels/map/` | `grep -rn "React.memo\|memo(" src/app/parcels/map/**` → 0 hits (excluding `useMemo`) |
| Heavy children are mounted unconditionally, so all of them re-render | `<FilterPanel>` `:6077` (779 lines) · `<ArchibaldChat>` `:6781` · `<SidePanel>` `:6788` (1,346 lines) |

MapLibre fires `mousemove` at pointer sample rate — 60 Hz on a standard display, 120+ Hz on a
high-refresh screen or a precision trackpad.

**The repo already diagnosed and fixed this exact disease, one line above, and missed this instance.**
`page.tsx:4388-4391` reads:

> `// map.on("zoom" / "rotate") → setState mirrors removed 2026-06-11`
> `// (perf fix on feat/keyboard-nav). … MapZoomReadout + MapCompassIcon`
> `// own their own rAF loops and read mapRef live.`

and `MapZoomReadout.tsx:5-14` states the cost outright: *"forcing a full MapPage re-render on every
camera tick … the parent reconciled its 8000-line JSX tree 60 times per second."* The zoom mirror
was removed. The cursor mirror on the line immediately above survived — and it feeds the very same
JSX line (`:5883`) as the component that replaced it.

**Proposed fix:** apply the established in-repo pattern. Extract a `MapCoordsReadout` component
modelled directly on `MapZoomReadout.tsx:23-45` — own rAF loop, `mapRef.current.getCenter()` or a
ref-held last pointer position, mutating `span.textContent` only when the formatted value changes —
then delete `cursor`/`setCursor` (`:1903`) and the handler at `:4387`. Zero parent reconciliation.

Note this leaves **no console trace**, which is exactly why audit 5.8 ("console is clean of errors")
and the live browser QA pass could not see it.

### CAUSE 3 · ~26 delegated layer listeners, each running its own `queryRenderedFeatures` per mousemove

**Severity: Medium · Confidence: Proven mechanism, count varies with loaded layers · Cost: continuous, compounds CAUSE 2**

MapLibre's `_createDelegatedListener` (verified in the `maplibre-gl@5.22.0` bundle) gives **each**
`map.on(type, layerId, handler)` binding its own delegate that calls
`this.queryRenderedFeatures(point, {layers})` per event — and the `mouseleave`/`mouseout` branch
*also* registers a `mousemove` delegate. So `mouseleave` bindings cost a query per mouse move too.

| Binding | Count | Proof |
|---|---|---|
| `bindLayerEvent(map, "mousemove", …)` | 12 | `page.tsx` — `:2966, :3008, :3015, :4122, :4660, :4679, :4794, :4819, :4842, :4865, :4891, :4914` |
| `bindLayerEvent(map, "mouseleave", …)` | 12 | `page.tsx` |
| Buildings hook | 2 | `useBuildingsLayer.ts:317, :318` |

Additionally, the three PMTiles fill handlers (all installed by `addLandTileSource`, called for
3 sources at `:4664-4666`) each run a **second, manual** `queryRenderedFeatures` inside the handler
body: `page.tsx:4135`.

**Honest bound on this one:** the delegate does `layers.filter(id => this.getLayer(id))` and skips
the query when nothing matches, so only bindings whose layer currently exists in the style actually
cost anything. On a default load that is the ZAAHI plot fill, the vault layer, the buildings
footprint and whichever overlays are toggled on — call it 6–10 live queries per mousemove, several
of them against PMTiles fills with thousands of features in the viewport. This is a real cost, but
it is a supporting player next to CAUSE 2, and its true weight is the main thing the profile in
[What to capture](#what-to-capture) should settle.

**Proposed fix:** MapLibre accepts an *array* of layer ids per binding
(`map.on("mousemove", [a, b, c], handler)`), collapsing N delegates into one query. Group the
mousemove bindings that share a popup discipline into a single binding with a dispatch on
`e.features[0].layer.id`, and drop the manual re-query at `:4135` by reading the already-queried
feature list. Sequence this **after** CAUSE 2 — with the re-render gone, this may fall below the
threshold of being worth the churn.

### CAUSE 4 · A 60 Hz `setPaintProperty` loop runs the whole time a parcel is selected

**Severity: Medium · Confidence: Proven · Cost: continuous while the side panel is open**

`page.tsx:1708-1725` — an rAF loop calling
`map2.setPaintProperty(ZAAHI_PLOTS_GLOW_CRISP, "line-width", w)` **every frame** while
`selectedParcelId != null` (`:1705`, deps `:1725`), to pulse a gold outline on a 1.5 s sine.

Each `setPaintProperty` marks the style dirty and schedules a MapLibre repaint, so selecting a
parcel pins the map at a continuous 60 fps redraw for as long as the panel stays open — on top of
whatever CAUSE 2 and CAUSE 3 are already charging per mouse move. It is deliberate (a designed
animation), so this is a cost/benefit call rather than a bug.

**Proposed fix:** the same visual is achievable with a MapLibre paint transition or by driving
`line-width` from a `feature-state` toggled twice per cycle rather than re-setting a paint property
60 times a second. If the pulse is founder-mandated as-is, cap it — e.g. run the pulse for 3 s after
selection and then settle at a static width — rather than running it unbounded.

### CAUSE 5 · A lost WebGL context is unrecoverable — this is the "hang"

**Severity: High (as a hang) · Confidence: the gap is proven; the trigger is not**

```
grep -rn "webglcontextlost\|webglcontextrestored" src/   →   0 hits
```

There is no context-loss handling anywhere in the codebase. When the browser drops the WebGL
context — for any reason, including routine GPU-driver resets and tab backgrounding under memory
pressure — MapLibre's canvas stops painting and nothing restores it. The chrome stays fully
interactive over a dead map. **That presentation is indistinguishable from a hang, and it is the
single defect here most likely to be what users are actually reporting.**

What can be ruled out, with proof:

| Hypothesis | Verdict | Proof |
|---|---|---|
| Context exhaustion (too many contexts) | **Ruled out — exactly 1 context on this route** | Only `page.tsx:4351` is reachable. `MiniMap.tsx:144` is unmounted (`page.tsx:2228` "MiniMap dock removed 2026-06-01"; `grep -rn "<MiniMap" src/` → 0 render sites). `CoordsEntry.tsx:141` mounts only inside the Add-Plot wizard (`Step1PlotLookup.tsx:716`). |
| deck.gl creating a second context | **Ruled out** | `interleaved: true` at `page.tsx:5020` — deck shares MapLibre's context. |
| Context leaked on re-render | **Ruled out** | Init effect is guarded (`page.tsx:4341`) with `deps: []` (`:4995`); overlay attach is guarded by `deckOverlayRef.current` (`:5004`). |
| Context leaked on basemap swap | **Ruled out** | `setStyle` reuses the canvas and context. `@deck.gl/mapbox@9.3.2` registers and deregisters its own `styledata` listener (`mapbox-overlay.js:193, :229`), so the overlay self-heals across swaps. Cleanup removes the control (`page.tsx:4985-4990`) *before* `map.remove()` (`:4992`). |
| Listener accumulation across style swaps | **Ruled out** | `_layerEventRegistry` (`page.tsx:324-343`) off()s the prior binding per `type::layerId`. The comment at `:316-323` records the earlier Firefox lockup this already fixed. The double init does **not** double the listeners. |

What remains open — two candidates, neither proven:

1. **`canvasContextAttributes: { preserveDrawingBuffer: true }`** (`page.tsx:4380`). The inline
   comment asserts *"Negligible perf impact."* That claim is unverified and is device-dependent;
   `preserveDrawingBuffer` prevents the browser from discarding the back buffer after compositing
   and can force an extra full-screen copy per frame, with correspondingly higher GPU memory
   pressure. It exists solely so `map.getCanvas().toDataURL()` works for the Site Plan PDF
   (`src/lib/generate-site-plan-pdf.ts`). **I am not ranking this as a cause — it needs measuring,
   not asserting**, and the comment should not be trusted as evidence either way.
2. **deck.gl attaching mid-rebuild.** The audit 1.7 trace places `[GLB] MapboxOverlay attached`
   *between* the two `[ZAAHI]` blocks — i.e. deck.gl grabs the shared context inside the CAUSE 1
   double-init window, while MapLibre is tearing down and rebuilding the style. Plausible, unproven.
   If CAUSE 1 is fixed this window closes on its own, which is a reason to fix CAUSE 1 first and
   re-test rather than to investigate this directly.

**Proposed fix — two parts, and part (a) is worth doing regardless of what causes the loss:**

**(a) Handle the loss.** Register `webglcontextlost` (with `preventDefault()`, which is what makes
restoration possible at all) and `webglcontextrestored` on `map.getCanvas()` inside the init effect.
On loss: show a visible "Map interrupted — reloading" state instead of a silently dead canvas. On
restore: re-run the style/overlay attach path. This converts a permanent hang into a recoverable
blip and is the highest-value item in this document per line of code.

**(b) Measure `preserveDrawingBuffer` before touching it.** If the profile shows it is material,
the fix is to make it conditional — create the map without it, and for PDF export draw one frame
into an offscreen context or briefly re-init. Do **not** simply remove it: it will silently break
the Site Plan PDF, which is a shipped feature.

## Classified as BENIGN — with the evidence, so these do not get re-investigated

### B1 · `Navigator LockManager … immediately failed` — multi-tab, working as designed

The question posed was whether this is multi-tab contention or genuine multi-client instantiation
in one page. **It is multi-tab.** Call-site count, repo-wide:

```
grep -rn "createClient(" src/   →   exactly 3
```

| Call site | Runtime | Shape |
|---|---|---|
| `src/lib/supabase-admin.ts:20` | server only | lazily cached singleton (`cached` at `:13`) |
| `src/lib/supabase.ts:19` | **server only** | module singleton; `persistSession: false, autoRefreshToken: false` (`:20`) |
| `src/lib/supabase-browser.ts:11` | browser | **module-level singleton**; `persistSession: true, autoRefreshToken: true` (`:12`) |

`src/lib/supabase.ts` never reaches the browser bundle — its only two importers are route handlers
(`src/app/api/users/sync/route.ts:4`, `src/app/api/parcels/submit/route.ts:5`). So the page
instantiates **exactly one** GoTrue client. Not per-render, not per-effect.

The message itself, traced through `@supabase/auth-js@2.102.1`:

- Thrown at `dist/main/lib/locks.js:156`, reachable **only** when `acquireTimeout === 0` (the
  `ifAvailable: true` branch) — i.e. only when another holder already has the lock.
- The sole `_acquireLock(0, …)` in `GoTrueClient.js` is `_autoRefreshTokenTick` at `:4157`.
- That tick runs on a **30-second timer** (`AUTO_REFRESH_TICK_DURATION_MS = 30 * 1000`,
  `lib/constants.js:6`) and the error is caught and swallowed at `:4185-4190`
  (`if (e.isAcquireTimeout …) this._debug(…)`).

Web Locks are scoped per-origin **across tabs**, so with several `zaahi.io` tabs open exactly one
wins each refresh tick and the others log this. That is the cross-tab refresh dedup working
correctly. It is off the render path, off the critical path, and fires at 1/30 Hz.

**Adjacent, and worth knowing but not a cause:** `src/lib/api-fetch.ts:16` calls
`supabaseBrowser.auth.getSession()` on *every* request, and `getSession()` takes the same
cross-tab exclusive lock with a **5-second** timeout (`GoTrueClient.js:2222`;
`lockAcquireTimeout: 5000` at `:28`). Under heavy multi-tab contention that is a theoretical
multi-second stall on an `apiFetch`. Fixing CAUSE 1 roughly halves this page's request count and
therefore its lock traffic, which is a free improvement here. Not worth pursuing on its own.

### B2 · `addSource`/`addLayer` do **not** re-upload on the second init

The second `[ZAAHI]` block *is* real double execution (SYMPTOM of CAUSE 1) — but the specific
question of whether `addSource`/`addLayer` with an existing id re-uploads is answered **no**:

- `page.tsx:3465-3470` — `if (plotSrc) setData(...)` else `addSource`
- `page.tsx:3544-3549` — same for the buildings source
- every `addLayer` is wrapped in `if (!map.getLayer(id))`: `:3484, :3504, :3517, :3526, :3556`

This also explains the shape of the observed trace: the run that logged `addSource`/`addLayer`
(`:3551`, `:3557`) was the one that found no existing source; the other logged only
`plotFeatures` (`:3439`) and `buildingFeatures count` (`:3543`) and fell through to `setData`.
Ordering follows from `map.once("styledata")` (`:5125`) firing before `map.on("load")` (`:4435`).

The real doubled cost is the **feature build plus two `setData` calls**, not layer creation.

### B3 · Buildings handlers on an empty source — negligible

`useBuildingsLayer.ts:190-199` has no `items.length === 0` early return, so it installs a source
(`:226-231`), fill/line layers, and click/hover handlers (`:280-324`) for a 0-item dataset. But the
handlers are ref-guarded (`:280` `if (!handlersInstalledRef.current …)`, set at `:322`) — installed
exactly once, no accumulation. Cost is two delegated `queryRenderedFeatures` against a 0-feature
layer per mousemove: real, negligible.

Audit 1.7's suggested early-return is still correct as **hygiene** and should be taken with the
logging cleanup — just not for performance reasons.

### B4 · deck.gl overlay lifecycle — clean

Guarded attach (`page.tsx:5004`), cleanup removes the control before `map.remove()` (`:4985-4992`),
and `@deck.gl/mapbox@9.3.2` manages its own `styledata` subscription (`mapbox-overlay.js:193, :229`).
No leak on re-render or basemap swap.

One non-perf defect noticed in passing, recorded so it is not lost: `mapStyleReady` is only ever set
`true`, at `page.tsx:4439`, inside the one-shot `map.on("load")` handler. The basemap-swap path
(`:5125`) never resets it, so the `[mapStyleReady]` effects (`:5031`, `:5051`) do not re-run after a
swap. deck.gl's own `styledata` listener covers the overlay, so this is currently harmless — but it
is a latent trap for anything else later added to those effects.

### B5 · Viewport feature counter — correctly gated

`page.tsx:2083-2127` runs `queryRenderedFeatures` over the viewport, but only while the FilterPanel
is open (`:2084`) and debounced 500 ms on `moveend` (`:2116-2120`). Working as intended.

### B6 · Production debug logging — hygiene, not perf

Audit 1.7's first bullet stands. `useBuildingsLayer.ts:164-175` is the worst of them — it `.map()`s
every returned item into a fresh object array purely to log it, which allocates and retains
references on every load. At `items: 0` that costs nothing today; it scales with the buildings
dataset. Gate all `[ZAAHI]`/`[BUILDINGS]`/`[GLB]` logs behind `NODE_ENV !== 'production'`.

## What to capture

A browser Performance profile **is** needed to rank CAUSE 2 against CAUSE 3 and to settle the
`preserveDrawingBuffer` question. Everything above stands on `path:line` evidence; the numbers below
are what is missing. Capture on a **production build against `zaahi.io`**, signed in, with a single
tab (all other `zaahi.io` tabs closed, so B1 does not add noise).

**Capture 1 — load cost (validates CAUSE 1 and sizes the win)**
- DevTools → Performance → check **Screenshots** → hard reload (Ctrl+Shift+R) → stop ~15 s after the map paints.
- Also keep the Network tab open with **Preserve log** and **Disable cache** off (production caching is what users get).

**Capture 2 — mousemove cost (ranks CAUSE 2 vs CAUSE 3)**
